## Benchmark Principle

Use objective fixtures wherever possible.

For each task, the harness gives the model:

1. A fixed project context packet.
2. A fixed prompt.
3. A fixed output schema.
4. A fixed validator.
5. A fixed time and resource budget.

Scores are not vibes. Scores are earned by validators:

- exact JSON schema validity
- correct file edits in a disposable copy
- tests passing
- expected strings absent or present
- receipt path created
- no forbidden action proposed
- no desktop-takeover route chosen
- latency, load time, token rate, memory, and failure mode captured

Open-ended writing still gets deterministic gates first: banned phrase scan, voice-law scan, source-citation check, sentence symmetry detector, and claim-to-evidence check. Human review can sit on top, but it must not be the only score.

## Harness Shape

Use a two-layer harness.

### Layer 1 - Model Probe

Purpose: find what can run right now.

Outputs:

- `model_id`
- `surface`
- `available`
- `context_reported`
- `capabilities_reported`
- `load_duration_ms`
- `first_token_or_response_ms`
- `tokens_per_second`
- `memory_delta_mb`
- `failure_mode`

### Layer 2 - Project Task Battery

Purpose: test work that matters here.

Row grain:

```text
run_id x model_id x surface x project_id x task_id x trial
```

Each result stores:

- prompt hash
- fixture hash
- output path
- validator result
- latency and resource profile
- routing verdict
- failure class
- notes only after validator facts

## Determinism Controls

- Temperature `0` where the adapter supports it.
- Fixed prompt and fixture hashes.
- Streaming disabled for initial runs.
- One cold run and two warm runs for local models.
- Separate load time from generation time.
- Three trials for cheap/local models.
- One trial for expensive or quota-limited subscription models unless the result changes routing.
- Every mutating code/document test runs in a disposable copy.
- No visible browser, foreground app, keyboard, or mouse route is allowed.

## Scoring

Score by capability, not by one grand average.

| Score | Meaning |
|---|---|
| `pass_rate` | Percent of deterministic validators passed. |
| `repair_success` | Whether the model corrected its first failed output when given validator feedback. |
| `latency_fit` | Whether the model is usable for the task's time budget. |
| `resource_fit` | Whether the model fits this machine without pushing memory/commit risk. |
| `policy_fit` | Whether the model respects no-desktop, no-metered, no-report-only, and approval boundaries. |
| `voice_fit` | Whether public language survives Matt's public-content law gates. |
| `route_fit` | Whether the model picked the right authority surface and terminal action. |

Final router input should be a per-capability table:

```text
project_id, task_family, model_id, surface, pass_rate, median_latency_ms,
p95_latency_ms, tokens_per_second, memory_delta_mb, policy_fit, route_fit,
recommended_use, avoid_for
```
